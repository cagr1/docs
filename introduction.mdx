OrchestOS orchestrates the coding CLIs you already use — Claude Code, Codex, OpenCode — behind a local dashboard. You describe what you want in a chat. The orchestrator turns the request into a task that declares which files may be written, an executor writes them inside a git worktree, deterministic checks and a QA reviewer validate the result, and only then does anything merge into your branch.

## The problem it solves

Delegating software work to an LLM usually means trusting a black box. You write a prompt, the agent edits files, and you hope it only touched what you asked for. When something breaks, you dig through a diff. There is no contract, no evidence, and no systematic check that the output meets your requirements.

OrchestOS removes both friction points:

- **The trust barrier** — every run produces an evidence record in SQLite: model, tokens, files attempted vs. authorized, check results, QA verdict, and context warnings.
- **The technical barrier** — you ask in plain language. OrchestOS drafts the task, picks the agent for each role, sets up the sandbox, and runs QA.

## Key differentiators

### Chat first, tasks second

The dashboard has two modes. **Chat** is a read-only conversation with the orchestrator about your project. **Dev** turns a request into a task card with its file contract. You approve tasks that touch existing files; new files run directly. The card updates in place as the task runs, fails, or is retried.

### Your CLIs, your plan

OrchestOS does not ship its own model. Each of the four roles — orchestrator, executor, reviewer, auxiliary — runs on an agent you choose: `claude`, `codex`, `opencode`, or `api`. With CLI agents, calls use the plan you are already logged into, and you need no API key. See [Model routing](/reference/models).

### Contract-first: declared output, hard enforcement

Every task includes an `output[]` list — the exact set of files the executor may write. Any write outside that list is blocked, logged, and fails the run.

```yaml
output:
  - src/components/Button.tsx
  - src/components/Button.module.css
```

### Sandbox via git worktrees

Each task runs in its own git worktree. On QA pass, the worktree merges back into your branch. On failure, it is discarded. Your branch is untouched until the output is verified.

### Deterministic checks before QA

Shell commands (typecheck, tests, grep assertions) run before the reviewer is called. The first failing check reverts the worktree and retries, so you only spend reviewer calls on output that is structurally sound.

```yaml
checks:
  - cmd: "bun run typecheck"
  - cmd: "bun test src/components"
```

### The reviewer validates acceptance criteria

After checks pass, the reviewer role evaluates each `acceptance_criteria` item. If any criterion fails, the worktree is reverted and the task returns to `pending`. After three QA failures the task becomes `failed_permanent`, and a diagnosis agent analyzes the run history to suggest a fix.

```yaml
acceptance_criteria:
  - "WHEN Button receives disabled=true THEN cursor-not-allowed and opacity-50 are applied"
  - "WHEN onClick is triggered THEN it is not called while disabled=true"
```

### SQLite evidence store

Every run writes a record to `~/.orchestos/db.sqlite`: agent and model, token counts, `snapshot_before` and `snapshot_after`, files attempted, authorized, and blocked, QA verdict, and context warnings. Every finished task also leaves a plain-text entry in **Memory**. Inspect it in the dashboard or with `orchestos runs --detail <run-id>`.

## How the pieces fit together

```text
chat request → task draft (output[]) → middleware chain → executor → contract check → checks[] → reviewer → merge / retry / failed_permanent
```

You decide what to build. OrchestOS decides how to verify it was built correctly.
