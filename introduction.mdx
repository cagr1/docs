OrchestOS gives you a local dashboard and CLI for coding tasks. You describe a change in chat. The orchestrator creates a task with declared output files, an executor performs the work, and the harness records checks and review evidence.

## Chat and tasks

Use **Chat** to discuss your project. Use **Dev** to request changes through the chat's `create_task` tool. A task card shows the contract, execution state, and result.

Tasks that touch existing files wait for **Approve & Run**. With `permissionMode: manual`, new-file tasks also wait. A dirty worktree requires a commit before execution. Interrupted tasks offer **Resume**.

## Agents and roles

Choose agents and models for Orchestrator, Executor, Reviewer, and Auxiliary in **Settings → Model routing**. Built-in task CLIs are Claude Code, Codex, and OpenCode. You can also configure API calls and custom CLI task engines. Calls through signed-in CLIs do not need API keys.

See [Model routing](/reference/models) for supported agents and the distinction between detecting a CLI and executing a task with it.

## File contracts

Every task declares a nonempty `output[]` list:

```yaml
output:
  - src/Button.tsx
  - src/Button.test.tsx
```

For API execution, OrchestOS validates returned file blocks before writing them. CLI execution also validates the contract and worktree changes after the agent edits. The output contract is not a general operating-system access boundary. See [File contracts](/concepts/contracts).

## Worktree isolation

The default `auto` sandbox uses a git worktree when your project has a clean tree and a usable branch. The executor and checks run there, and successful changes merge into the base branch. Without git or a usable branch, execution can fall back to the current directory. See [Sandbox](/concepts/sandbox).

## Verification

Deterministic checks run before LLM review. You can declare commands and a timeout for each check; the default is `60000` milliseconds.

The reviewer runs when you supply acceptance criteria, an applicable review gate requires it, or your profile says you do not write code. Otherwise the evidence records `qa_verdict: skipped`.

```yaml
checks:
  - bun run typecheck
acceptance_criteria:
  - "WHEN disabled is true THEN clicking does not call onClick"
```

Failed checks or review normally return a task to `pending` with an incremented retry count. The third failed attempt becomes `failed_permanent`. Other execution failures can set `failed` earlier, and dependencies or missing toolchains can block work.

## Evidence

Runs record model and provider information, file evidence, snapshots, check results, and the QA verdict in `~/.orchestos/db.sqlite`. Task outcomes also leave memory entries. Inspect a task card, **Settings → your project → Runs**, or:

```bash
orchestos runs --detail <run-id>
```

Start with [Quickstart](/quickstart) to run a task and read its evidence.
