Specs live in `.orchestos/specs/<task-id>.md`. In the dashboard, open **Settings → your project → Specs**.

## Create or draft

Create a template, then edit its content:

```bash
orchestos spec create add-health --project ./my-project
```

To draft with an LLM, you must supply a description:

```bash
orchestos spec draft add-health --project ./my-project --description "Add a health endpoint"
```

For a task that needs design review:

```bash
orchestos spec create add-auth --design --project ./my-project
orchestos spec draft add-auth --design --project ./my-project --description "Design authentication for the API"
```

`--design` marks the design as `pending` and adds design content to the workflow. Review that content before approving it.

## Review and approve

```bash
orchestos spec show add-auth --project ./my-project
orchestos spec lint add-auth --project ./my-project
orchestos spec approve-design add-auth --project ./my-project
orchestos spec approve add-auth --project ./my-project
```

`design` is either `pending` or `approved` when present. `spec approve` refuses a pending design, pending clarification, or invalid spec. Resolve clarification by setting `clarify` to `resolved` or `none`. Approval records `status: approved` and its timestamp. Keep the template's `## Criterios de aceptación` heading: approval validation requires that section and at least one real criterion.

`spec lint` reports criterion-format and delta-header findings and exits with status `1` when it finds them. Its findings are advisory; approval runs its own validation.

## List and archive

```bash
orchestos spec list ./my-project
orchestos spec list ./my-project --all
orchestos spec archive add-auth --project ./my-project
```

The default list omits archived specs; `--all` includes them.

## Execution gate limitation

The task harness checks the spec before sandbox setup when its supplied configuration has `requireSpec: true`. See the [config reference](/reference/config) for a current limitation.
