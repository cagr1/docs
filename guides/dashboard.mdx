The dashboard is the main way to use OrchestOS. You talk to the orchestrator in a chat, approve the tasks it drafts, and watch them run in the same thread. It reads and writes the same SQLite database as the CLI.

## Starting the dashboard

```bash
orchestos dashboard              # http://localhost:4242
orchestos dashboard --port 3000
```

<Note>
  The dashboard binds only to `127.0.0.1`, so it is not exposed on your network. Mutating requests are same-origin checked, so no other page on your machine can trigger actions against it.
</Note>

The UI is a React app built with `bun run build:app`. `orchestos dashboard` rebuilds it automatically if the build is missing.

## Projects

Add a project from the sidebar — any local git repository. Each project keeps its own tasks, runs, memory, specs, skills, and instincts.

## Chat and Dev modes

A switch at the top of the thread selects the mode:

- **Chat** — a read-only conversation with the orchestrator about the project. It creates no tasks and writes no files.
- **Dev** — ask for a change. The orchestrator drafts a task with its `output[]` contract and shows a task card in the thread.

The thread shows live thinking, collapsible tool calls, and one card per task. You can attach files: images go natively to the CLI; text and PDF are inlined.

## Task cards

Each task card shows what the task will write and offers the next action:

| Button | When it appears |
|--------|-----------------|
| **Approve & Run** | The task touches existing files. It waits for your confirmation. Tasks that only create new files run directly. |
| **Commit & Run** | Your working tree is dirty. You choose which files to commit before the task starts. |
| **Retry** | After a failed attempt. Earlier attempts stay folded inside the card. |

The card updates in place: running → done or failed, with the executor's model, the attempt number, and a summary.

## Settings

### Global

**General**, **Health**, **API & Models**, **Model routing**, **Executor**, **Usage**, **Danger zone**, and **Language**.

**Model routing** is where you assign agent, model, and effort to the four roles. See [Model routing](/reference/models).

### Per project

Under each project's name:

| Section | What it shows |
|---------|---------------|
| **Tasks** | Every task with status, retry count, QA verdict, and its detail |
| **Runs** | Run evidence: agent and model, tokens, files written or blocked, checks, QA verdict, context warnings |
| **Graph** | The indexed code graph used for context suggestions |
| **Memory** | One plain-text entry per finished task (`task/<id>`: files, QA verdict, model), written without an LLM call |
| **Specs** | Specs with their lint status; approve them here |
| **Skills** | Skills available to the project |
| **Instincts** | Learned behaviors; approve or reject auto-proposals |
| **Plan** | The project plan |

## The dashboard and the CLI

Both use `~/.orchestos/db.sqlite` and the project's `tasks.yaml`. A task run from the CLI appears in the dashboard and the other way round. See the [CLI reference](/reference/cli).
