A task describes one change. You declare its input files, allowed output files, checks, and acceptance criteria in `tasks.yaml`.

```yaml
tasks:
  - id: update-button
    description: Add a disabled state to the button
    input: [src/Button.tsx]
    output: [src/Button.tsx, src/Button.test.tsx]
    task_class: implement
    checks:
      - bun run typecheck
    acceptance_criteria:
      - "WHEN disabled is true THEN clicking does not call onClick"
```

Use a unique lowercase ID such as `update-button`. You must supply a description and a nonempty `output` array. Omitted `input` becomes `[]`.

## Run a task

```bash
orchestos task run --explain update-button
orchestos task run --id update-button
orchestos task status
```

`--explain` prints task metadata, the resolved model and executor, input files, checks, and criteria. It does not build the full enriched prompt or call a model.

The dashboard creates tasks through the chat's `create_task` tool. You review the resulting card in the same conversation. See [Dashboard](/guides/dashboard).

## Follow the state

| State | Meaning |
| --- | --- |
| `pending` | Waiting to run or waiting after a failed attempt. Read `retry_reason`. |
| `running` | Execution is in progress. |
| `done` | Execution and the applicable verification steps finished successfully. |
| `failed` | An execution error stopped the attempt. |
| `failed_permanent` | The three-attempt limit was reached. |
| `blocked` | A dependency or required toolchain prevents execution. |

Check and QA failures normally increment `retry_count` and return the task to `pending`. At the third failed attempt it becomes `failed_permanent`. Other errors can set `failed` immediately. A dirty tree or insufficient context budget can keep a task pending without consuming an attempt.

You can inspect `retry_reason`, `qa_verdict`, and `run_id` to understand the result. `done` does not imply that an LLM reviewer ran: review can be `skipped`.

Use `depends_on` for prerequisites. `--all` runs ready pending tasks, stops on failure or blockage, and caps the loop at 20 iterations. Parsing catches duplicate IDs but does not reject cycles.

See the [tasks.yaml reference](/reference/tasks-yaml) for routing fields, `approvalMode`, `planner_model`, and every check option.
