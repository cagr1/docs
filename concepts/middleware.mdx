The harness prepares each task in this order:

```text
spec gate → sandbox → classification and routing
  → skillRoute → roadmapContext → contextInject → instinctApply
  → prompt
```

## Harness stages

The spec gate checks for an approved spec when the supplied harness configuration enables `requireSpec`. See [Specs](/guides/specs).

Sandbox setup selects a worktree or the current directory. Classification uses `task_class` when present and otherwise classifies the description. Routing resolves the executor and reviewer. See [Sandbox](/concepts/sandbox) and [Model routing](/reference/models).

## The four middleware steps

| Step | What it adds |
| --- | --- |
| `skillRoute` | The primary skill and applicable automatic phase skills. Review-only skills stay in the QA path. |
| `roadmapContext` | Applicable engineering guides and the project profile. Missing required toolchains can block a task. |
| `contextInject` | `CONTEXT.md` when it exists, overriding the supplied project context. Otherwise it keeps that context. |
| `instinctApply` | Actions from verified instincts with confidence at least `0.8`, scoped to the registered project. |

After the chain, the harness builds the executor prompt from context, skills, roadmap guides, instinct actions, task instructions, explicit input files, and the output contract. Omitted `input` stays `[]`.

## Control task context

```bash
orchestos context compress ./my-project
orchestos instinct add --trigger "Billing convention" --action "Use src/billing/stripe.ts for Stripe calls"
orchestos task run ./my-project --explain add-health
```

`--explain` prints the model, executor, declared inputs, checks, criteria, and task metadata. It does not render this full middleware context.
