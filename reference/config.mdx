OrchestOS tries `<project>/orchestos.config.yaml`, then `~/.orchestos/config.yaml`, then built-in defaults. The first readable, parseable file wins. It does not merge project and global settings. Each selected file is resolved against defaults. Custom CLI declarations are always read separately from the global file.

## Create and inspect

```bash
orchestos config init ./my-project
orchestos config show -p ./my-project
```

`config init` refuses to overwrite an existing file. It writes the legacy `models` scaffold with OpenRouter `deepseek/deepseek-v4-flash` entries for `planner`, `executor_heavy`, `executor_light`, and `default`. Its `qa` and `roles` examples are commented out. It does not write a complete configuration for all four roles.

## Fields

| Field | Behavior |
| --- | --- |
| `config_version` | Schema version; use `1`. |
| `roles` | Assign `orchestrator`, `executor`, `reviewer`, and `auxiliary` using `{ agent, model, effort?, provider? }`. Agent and model are required nonempty strings. |
| `roles.*.agent` | `claude`, `codex`, `opencode`, `api`, or an ID declared in global `clis`. The role loader does not accept `local`. |
| `taskAgentRules` | Routing rules with `match: { output?: [...], skill?: id }`, `agent`, optional `model`, and `cli_effort`. Task agents include `local`, `api`, registered task CLIs, and custom CLI IDs. |
| `agent` | Saved agent preference. Task execution still resolves the Executor role or a task override. |
| `permissionMode` | `yolo` (default) or `manual`. Manual holds chat-created tasks for approval, including new-file tasks. Existing-file tasks are held in either mode. |
| `apiMode` | `single-shot` (default) or `agentic` for API execution. |
| `agentic.maxIterations` | Integer from `1` to `100`; default `15`. Limits tool-use rounds per attempt. |
| `external.timeoutMs` | Integer from `60000` to `86400000`; default `1200000`. Limits a CLI call's wall-clock time. |
| `sandbox.derivedFiles` | Exact relative file paths that sandbox setup may discard when dirty. No absolute paths, backslashes, parent traversal, or directory paths. |
| `clis` | Executable declarations from `~/.orchestos/config.yaml` only. Project declarations are ignored with a warning. |

Invalid role assignments are ignored with a warning. A missing role raises `RoleUnassignedError` when needed. Explicit `null` unassigns a role, including one that could otherwise migrate from legacy settings.

<Warning>
  The harness has a `requireSpec` gate, but the current YAML loader does not retain `requireSpec`. Setting it in a YAML file alone does not activate that gate.
</Warning>

## Example

Choose models available in your own CLI or provider catalog. This example uses model IDs present in the shipped scaffold:

```yaml
config_version: 1
roles:
  orchestrator: { agent: claude, model: claude-sonnet-4-5 }
  executor: { agent: codex, model: gpt-6-luna, effort: medium }
  reviewer: { agent: api, provider: openrouter, model: openai/gpt-4.1 }
  auxiliary: { agent: api, provider: openrouter, model: deepseek/deepseek-v4-flash }
permissionMode: manual
apiMode: single-shot
agentic:
  maxIterations: 15
external:
  timeoutMs: 1200000
sandbox:
  derivedFiles: [reports/generated.json]
taskAgentRules:
  - match: { output: ["apps/api/**"] }
    agent: codex
    model: gpt-6-luna
```

Edit **Task rules** inside **Settings → Model routing** (`routing-rules`). Output glob matches take precedence over skill matches. The first match in each category wins. Rules are applied when a task is drafted.

## Custom CLIs

Declare custom CLIs only in `~/.orchestos/config.yaml`. Each entry requires `id`, `label`, `command`, and a string array `args`. Optional fields are `modelArgs`, `models`, and `timeoutMs`. The timeout uses the same `60000`–`86400000` range.

Use the raw custom ID in `roles.*.agent` and task rules. Use `cli:<id>` as a task's `engine`. A custom CLI task engine requires a worktree. It does not guarantee read isolation or action approvals. Its `args` can contain `{prompt}`; otherwise the prompt goes to stdin. `modelArgs` can contain `{model}`.

Although the role loader accepts custom IDs, helper calls through a role still need a chat adapter. A generic task executor does not add that adapter; assigning it to a helper role can fail.

## Legacy settings

`models.planner`, `models.executor_heavy`, and `models.qa` can migrate to API role assignments for Orchestrator, Executor, and Reviewer when no explicit role is set. `models.executor_light` and `models.default` remain parsed. The loader also translates older `executor_mode` and `executorEngine` values in memory.
