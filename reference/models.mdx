Open **Settings → Model routing** to assign Orchestrator, Executor, Reviewer, and Auxiliary. Each assignment contains an agent and model, with optional effort and API provider.

| Role | Responsibility |
| --- | --- |
| Orchestrator | Chat and task drafts. |
| Executor | Writes task output. |
| Reviewer | Reviews criteria and applied review gates. |
| Auxiliary | Diagnosis, analysis, and memory judging. |

A role has no built-in model assignment. When a call needs an unassigned role, it fails with a message such as `Executor role is unassigned — assign it in Settings → Model routing`.

## Agents and engines

Task routing accepts `local`, `api`, the registered task CLIs, and custom CLI IDs. Role configuration accepts `claude`, `codex`, `opencode`, `api`, and globally configured custom IDs. The current role loader rejects `local`.

| Task engine | Execution |
| --- | --- |
| `single-shot` | One API response parsed into file output. |
| `agentic` | API tool-use loop. |
| `external` | Claude Code CLI. |
| `codex` | Codex CLI. |
| `opencode` | OpenCode CLI. |
| `cli:<id>` | A custom CLI declared in global `clis`. |

The CLI registry also detects `deepseek`, `gemini`, `kimi`, and `glm` binaries. Detection does not mean they have a built-in task executor or chat adapter. The shipped task engines cover Claude Code, Codex, OpenCode, and globally configured custom CLIs.

Custom CLI IDs are used directly in `roles.*.agent`; the `cli:` prefix belongs to task engines. Generic CLI execution requires a worktree and does not provide verified read isolation or action approvals. A custom task engine does not add the chat adapter needed for helper role calls; those calls can fail.

## Task overrides

Use `engine`, `executor_model`, and `cli_effort` in `tasks.yaml` to choose task execution. `task run --engine` and `--model` override one invocation without persisting those values in the task file.

If you select a different CLI from the configured Executor, supply its model. OrchestOS does not silently choose one for that CLI.

`task_class` selects automatic phase skills. It accepts `plan`, `implement`, `fix`, `review`, or `doc`. Without it, the harness classifies the task description.

## Task rules

**Task rules** is a row within **Settings → Model routing**, anchored as `routing-rules`.

```yaml
taskAgentRules:
  - match: { output: ["apps/api/**"] }
    agent: codex
    model: gpt-6-luna
  - match: { skill: frontend-design }
    agent: claude
    model: claude-sonnet-4-5
```

An output glob match takes precedence over a skill match. The first matching rule in each category wins. Rules supply fields when the task is drafted. Include `model` when a rule selects a CLI different from the Executor agent.

## Review and API calls

The Reviewer role resolves before task execution. The LLM review call runs only when criteria, an applicable review gate, or the noncoding profile requires it. Otherwise the run records `skipped`.

Choose different executor and reviewer models when you want an independent assessment. If both resolve to the same agent and model, the harness logs a correlated-errors warning.

For `agent: api`, set `provider` to `openrouter`, `anthropic`, or `openai` and configure its key. CLI calls use the CLI's existing sign-in session. Model availability comes from the provider or installed CLI catalog.

## Migrating from the legacy models block

When no explicit role overrides it, `models.planner` can supply Orchestrator, `models.executor_heavy` can supply Executor, and `models.qa` can supply Reviewer as API assignments. Explicit `null` unassigns a role. Auxiliary has no equivalent legacy assignment.

See [Configuration file](/reference/config) for fallback rules and the legacy scaffold written by `config init`.
