OrchestOS routes every model call through one of four roles. Each role is an assignment of `{ agent, model, effort }` that you choose. OrchestOS never picks a model for you: a role uses exactly what is configured, and an unassigned role stops with an error asking you to assign it.

## The four roles

| Role | Used for |
|------|----------|
| `orchestrator` | The chat, and drafting tasks from your requests |
| `executor` | Running a task — writing the files in `output[]` |
| `reviewer` | The QA verdict on each acceptance criterion |
| `auxiliary` | Read-only helper calls: failure diagnosis, the memory judge, and the skill helpers in Settings |

```yaml
# orchestos.config.yaml
config_version: 1
roles:
  orchestrator: { agent: claude, model: claude-opus-5-5, effort: medium }
  executor:     { agent: codex,  model: gpt-6-luna,      effort: medium }
  reviewer:     { agent: codex,  model: gpt-6-luna,      effort: medium }
  auxiliary:    { agent: codex,  model: gpt-5.6-luna }
```

Edit roles in **Settings → Model routing**, or by hand in the file.

## Role fields

<ParamField path="agent" type="string" required>
  Who runs the call:

  - `claude` — the Claude Code CLI
  - `codex` — the Codex CLI
  - `opencode` — the OpenCode CLI
  - `api` — a direct API call through a provider (needs an API key)

  CLI agents use the plan you are already logged into. Only `api` costs money per call.
</ParamField>

<ParamField path="model" type="string" required>
  The model ID passed to the agent. For CLI agents this is the CLI's own model name. For `api`, it is the provider's model ID (for example `anthropic/claude-haiku-4-5` on OpenRouter).
</ParamField>

<ParamField path="effort" type="string">
  Reasoning effort passed to the CLI as-is. Its meaning belongs to the CLI that interprets it; OrchestOS does not validate levels per engine.
</ParamField>

<ParamField path="provider" type="string">
  Only for `agent: api`. Defaults to `openrouter`. Other values: `anthropic`, `openai`.
</ParamField>

## How a task picks its executor

For each task run, OrchestOS resolves the executor in this order:

1. **The task's own engine and model** — if the task sets `engine` (`external` for Claude, `codex`, or `opencode`) and `executor_model`, that wins. If it sets `engine` without `executor_model`, it reuses the Executor role's model only when the Executor uses that same CLI; otherwise the run fails with an error naming the mismatch.
2. **The task's own API model** — if the task sets `executor_model` without a CLI engine, it runs as an `api` call through the task's `executor` provider.
3. **The Executor role** — otherwise, the task uses `roles.executor`.

The reviewer always comes from `roles.reviewer`.

```yaml
# tasks.yaml — pin one task to a specific CLI and model
- id: design-api-interface
  engine: external                 # Claude Code
  executor_model: claude-opus-5-5
  description: "Design the auth service API with token refresh and revocation"
  output: [docs/api-auth.md]
```

<Note>
  Tasks still record a `task_class` (`plan`, `implement`, `fix`, `review`, `doc`) for observability, but the class no longer selects a model. Earlier versions routed by keyword to `planner` / `executor_heavy` / `executor_light`; that routing was replaced by the roles.
</Note>

## Task rules

When you work across several CLIs, you can send specific tasks to a specific agent with declarative rules. They are applied when a task is drafted and written into the task's `engine`, `executor_model`, and `cli_effort` fields. Edit them in **Settings → Task rules** or in the config file:

```yaml
taskAgentRules:
  - match: { output: ["apps/api/**"] }   # glob against the task's output[]
    agent: codex
    model: gpt-6-luna
    cli_effort: high
  - match: { skill: frontend-design }    # exact skill id
    agent: claude
    model: claude-opus-5-5
```

- An `output` match takes priority over a `skill` match.
- The first matching rule in declaration order wins; rules are not merged.
- A rule that routes away from the Executor's agent must set `model`.

## Migrating from the legacy `models:` block

Older configs used `models.planner / executor_heavy / executor_light / default / qa`. These keys are still parsed. When a role is not set explicitly, OrchestOS migrates:

| Legacy key | Becomes |
|------------|---------|
| `models.planner` | `roles.orchestrator` (as `agent: api`) |
| `models.executor_heavy` | `roles.executor` (as `agent: api`) — skipped if the project's `agent` is a CLI |
| `models.qa` | `roles.reviewer` (as `agent: api`) |

`executor_light` and `default` have no role equivalent. An explicit `roles.<name>` always wins; set it to `null` to unassign a role that would otherwise be migrated.
